## 1. Positioning sentence

> UCompute runs small open models on your own computer through a pinned llama.cpp engine with a local OpenAI-compatible API; when you pair a second device you own with a short code, it refuses every off-device request until you allow that device, and it records each off-device request it does run without the prompt or the response.

Claims: [`run-local`] [`engine`] [`openai-clients`] [`mesh-pair-choose`] [`local-only`] [`audit`]. Qualifiers that travel with it: development builds, October 2026; demonstrated on one Apple M2 Mac (macOS 26.2) and one Windows 11 laptop (Intel Arc 140V), both experimental, no platform declared supported [`platforms`]; downloading a model or the engine uses the internet [`local-only`]; the device that runs your request processes your prompt, so pair only devices you control or trust [`device-sees-prompt`]; each request runs whole on one device and UCompute does not split a model across devices [`mesh-pair-choose`].

Why this sentence and not the previous one. "Pair your own devices and choose which one runs a request" is now a category description: NVIDIA PAIR ("PAIR routes each independent request to one node", https://github.com/NVIDIA/Personal-AI-Router), LM Studio's LM Link ("load remote models as if they were local", https://lmstudio.ai/link) and Mesh LLM ("If one node can host the full model, it serves the model locally without stage traffic", https://github.com/Mesh-LLM/mesh-llm) all ship it with installers. The two properties no competitor page read on 2026-10-30 documents are the paired-but-closed default and the prompt-free audit log (`research/COMPETITORS.md`, verdict table). They lead. Whole-request-on-one-device is stated as a limitation, in the qualifier, never as a headline.

## 2. Three proof points

Each is a demonstrated behaviour with a registry id, the evidence the registry cites, and what the competitor pages say in their own words. None is a superlative.

### 2.1 Default-deny off-device policy [`local-only`, with `device-sees-prompt` beside it]

What is true: "Your prompts and responses stay on your device unless you pair another device and choose to run a request there. Local-only mode refuses every off-device request." Evidence: snapshot 8.8; F-06-02, F-10-10, F-06-07. Required context: the device that runs the request processes the prompt; downloading uses the internet.

Why it is a proof point: "bind to localhost by default" is universal (Ollama 127.0.0.1, https://docs.ollama.com/faq; llama-server `--host` default 127.0.0.1, https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md; Jan 127.0.0.1, https://docs.jan.ai/desktop/api-server; PAIR proxies "accept requests only from the local system", https://build.nvidia.com/rtx/pair.md). What no page read documents is a device that is already paired yet serves nothing until its owner allows it (`research/raw/competitors-positioning.md` section 4). The market's own argument for the default is the exposure record of unauthenticated servers bound to 0.0.0.0: Cisco Talos counted 1,139 reachable Ollama endpoints (https://blogs.cisco.com/security/detecting-exposed-llm-servers-shodan-case-study-on-ollama), Censys 10.6K (https://censys.com/blog/ollama-drama-investigating-the-prevalence-of-ollama-open-instances-with-censys), LeakIX 12,269 (https://blog.leakix.net/2026/02/ollama-exposed/). Cite these as findings about a configuration, with the note that the three counts use different scanners and filters and are not comparable; never as a statement that UCompute is safer. A larger January 2026 figure circulates in security press; the primary report was not read, so it is **unverified** and is not used.

### 2.2 Audit log without the prompt or the response [`audit`, `audit-detail`]

What is true: "Audit logs record each off-device request without the prompt or the response." The writer refuses fields named prompt, content, messages, api_key, private_key or pkcs8 and any string over 2 KiB; files rotate at 8 MiB; owner actions and revocations go to a separate security trail. Mechanics held by automated tests on one computer; absence of prompt text checked in the two-machine runs. On Windows the files carry the profile folder's access rights and second-account access is untested.

Why it is a proof point: no competitor page read documents an audit log of off-device requests. PAIR's SECURITY.md states a logging policy (prompts "should not be written to logs") but documents no audit log (https://github.com/NVIDIA/Personal-AI-Router/blob/main/SECURITY.md); LeakIX notes "Ollama doesn't log requests by default" (https://blog.leakix.net/2026/02/ollama-exposed/); Cisco's recommendations for exposed LLM servers include audit logging (https://blogs.cisco.com/security/detecting-exposed-llm-servers-shodan-case-study-on-ollama). The audience that checks privacy claims does it by reading source or capturing traffic (Ollama #2567, https://github.com/ollama/ollama/issues/2567; the local-llm.net audit method, https://www.local-llm.net/blog/local-ai-privacy-audit/). Until source is published this proof point is a documented design with test evidence, and the ready piece `content/ready/2026-10-30-what-the-audit-log-records.md` says so.

### 2.3 A complete trust lifecycle: pair, allow, audit, revoke [`mesh-pair-choose`, `transport`, `revocation`, `connect-by-address`]

What is true: pairing by short code; QUIC with TLS 1.3 and device keys pinned at pairing, both ends authenticated; "Your device will not send work to a device you have not paired"; revoke at any time, connection closed in 0.002 s to 0.061 s in four two-machine runs and the next request refused (never say what the revoked device is told); connect-by-address where a network blocks discovery, with the key still required. Tested between one Mac and one Windows laptop, and that Mac and one Linux desktop (processor only, development daemon started by hand; Linux is planned, not supported). Pairing between two Macs is not yet shown to work.

Why it is a proof point, and its exact standing: against the partitioning projects it is differentiated, because they document no device authentication (exo: "this is intended behaviour, exo's api is unauthorized", https://github.com/exo-explore/exo/issues/1833; llama.cpp RPC README: "the functionality is fragile and insecure", https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md). Against PAIR, LM Link and Mesh LLM, encrypted authenticated transport is parity, and per-device revoke is **parity with PAIR**: its README documents removing a node from the member list in its settings, which any member can do (`research/COMPETITORS.md`, re-check 2026-10-30). What remains specific to UCompute's evidence: per-device pinned keys rather than a shared token or a PIN (PAIR's own SECURITY.md: the six-digit PIN "is low entropy"), a measured revoke time, and the paired-but-closed default in 2.1. Revoke is the last step of the lifecycle, not a headline.

Supporting, honest, not a position: memory-fit verdict before download with size and license shown and SHA-256-verified downloads [`catalog-fit`] and official OpenAI clients working by changing the base URL [`openai-clients`]. llama-server ships `--fit` on by default (https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), and every competitor exposes `/v1`. The one documented opening is the pre-download verdict: Ollama #10920 asked for exactly that after a four-hour download failed the memory check at load, and the maintainer declined (https://github.com/ollama/ollama/issues/10920). Use it as a Run explainer, not a headline (`content/ready/2026-11-01-memory-fit-explainer.md`).

## 3. What we deliberately do not claim

- Not stronger, faster, or more private than any project. All tokens-per-second figures are path checks on models up to 0.5B, labelled "path check, not performance" (`claims/REGISTRY.md`, Numbers).
- Not novel in routing a whole request to one of your devices (PAIR, LM Link, Mesh LLM). Not pooling, not partitioning, not a scheduler, not an open network, not credits, not cloud: planned with no date, and introduced only as direction [`planned`, `direction`].
- Not supported on any platform. Demonstrated on one Mac and one Windows laptop; Linux, other GPUs and phones are planned [`platforms`]. Not shown between two Macs. No Linux package, no container image, no auto-update, no relay or NAT traversal, no mobile.
- Not reachable off the local network. Same network only; where client isolation also blocks unicast, pairing will not work (the limit flux #127 states for its own design, https://github.com/bjarneo/flux/issues/127).
- Not verified for tool calling; chat and completions with streaming are verified with the official OpenAI Python and JavaScript clients [`openai-clients`]. Whether `/v1/responses` or embeddings exist is **unverified** and is a question for Engineering (`research/raw/audience-ai-app-builders.md` section 8).
- Not downloadable, not open for sign-in, not a public source repository. "UCompute's code is licensed under Apache-2.0. The source has not been published yet." Both sentences travel together [`license`].
- Not immune to exposure. Default-deny is a build property and a configuration; no public build has been audited (`research/raw/adoption-barriers.md`, barrier 10).
- Not signed or notarized installers (`research/raw/adoption-barriers.md`, barrier 1).
- Never that a competitor is insecure. Their own documents are quoted where they describe their own trust boundary; absence from a page is never stated as absence of a feature (`research/raw/search-demand.md` section 14).

### 4.1 Ollama (MIT, 185.3k stars, v0.40.13 on 28 Oct)

- Their words: "Get up and running with Kimi, GLM, MiniMax, DeepSeek, gpt-oss, Qwen, Gemma and other models." (https://github.com/ollama/ollama). "Ollama binds 127.0.0.1 port 11434 by default. Change the bind address with the `OLLAMA_HOST` environment variable." (https://docs.ollama.com/faq). "The local API at `http://localhost:11434` does not require authentication." (https://docs.ollama.com/api/authentication). The 2023 request for built-in auth was closed as not planned with "add an authenticating proxy in front of Ollama" (https://github.com/ollama/ollama/issues/849); later requests #1053, #8536 and #19045 drew the same answer or none (https://github.com/ollama/ollama/issues/8536, https://github.com/ollama/ollama/issues/19045).
- Ahead: macOS, Windows, Linux and Docker; a curated model library and one-command run ("ollama solved the UX problem", https://news.ycombinator.com/item?id=47788385); `/v1/responses` and audio endpoints (https://docs.ollama.com/api/openai-compatibility); a documented local-only switch `OLLAMA_NO_CLOUD=1` (https://docs.ollama.com/faq); the company's own figure of "over 8.9 million developers every month" as reported by TechCrunch (https://techcrunch.com/?p=3140214; company figure, not independently verified).
- UCompute differs: the HTTP API binds loopback by default and a non-loopback bind without an API key is refused at startup (corrected 2026-10-30: an exposure setting exists but is key-gated; the engine's own port has no exposure setting); off-device requests go only to a device you paired, over QUIC with TLS 1.3 and pinned keys, and a paired device still refuses them until allowed [`transport`, `local-only`]; each off-device request is logged without prompt text [`audit`]; the engine is a pinned llama.cpp release, named and credited [`engine`]; size, license and memory-fit are shown before a download [`catalog-fit`].
- Do not say: anything that reads as "Ollama is insecure"; any speed comparison; the circulating 175,000-host figure (primary not read, **unverified**).

Status on 2026-10-30 is **unverified** (lmstudio.ai unreachable in the re-check).

### 4.3 NVIDIA PAIR (Apache-2.0, 1.7k stars, v1.0.0 on 13 Oct; first release 26 Aug)

- Their words: "a local inference router for a group of compatible computers on the same network." "PAIR routes each independent request to one node." It "does not combine GPU memory, join GPUs into one larger GPU, or split a model or request across systems." "Released installers are signed." (https://github.com/NVIDIA/Personal-AI-Router). "The six-digit PIN is low entropy"; peer traffic is "designed to use certificates and mutual TLS after pairing", "only when identity and certificate material are present"; "Discovery and node-information traffic can use plain HTTP"; prompts "should not be written to logs" (https://github.com/NVIDIA/Personal-AI-Router/blob/main/SECURITY.md). "Updates are manual and per machine"; if discovery fails "you can add it by IP address" (https://docs.nvidia.com/local-ai/nvpair/getting-started/). Node removal: "Remove it from another node, which any member can do" from the settings page, per the README read in the 2026-10-30 re-check (`research/COMPETITORS.md`); no certificate revocation or rotation is described there, and the SECURITY.md lists member removal as needing "focused review and tests".
- Ahead: signed installers for Windows, Linux (.deb) and macOS; a 1.0 release; works with Ollama, LM Studio and llama.cpp as engines; Anthropic Messages, Ollama and OpenAI proxies (https://github.com/NVIDIA/Personal-AI-Router); mixed-OS pairing documented.
- Parity, stated as such: whole request to one device; PIN-based pairing; encrypted authenticated transport; per-device removal; add-by-address when discovery fails; a Windows firewall step (UCompute's rule covers only its own program on private networks, and Windows asks for administrator approval [`windows-firewall`]).
- UCompute differs, as facts and not as a ranking: device keys are pinned at pairing and the handshake fails before application data if a key is not pinned [`transport`]; revoke measured at 0.002 s to 0.061 s in four runs, next request refused [`revocation`]; a paired device refuses off-device work until allowed [`local-only`]; an audit log is documented, with the fields it refuses [`audit-detail`]; UCompute runs its own pinned llama.cpp rather than requiring another runner [`engine`]. PAIR's candour in its SECURITY.md is the tone to match; it is also the comparison target named in W44.
- Do not say: "PAIR has no revocation" (its README documents removal); "PAIR's PIN is weak" (quote the SECURITY.md sentence and stop); anything about PAIR's hardware floor relative to UCompute's (**unverified**).

### 4.4 Mesh LLM (Apache-2.0, 3.7k stars, v0.78.1 on 05 Oct)

- Their words: "Distributed AI/LLM for the people. Share compute privately or publicly to power your agents and chat." "experimental distributed-systems software." "If one node can host the full model, it serves the model locally without stage traffic." "QUIC end-to-end encrypts traffic between Mesh nodes." `mesh-llm.exe` "is not code-signed yet" (https://github.com/Mesh-LLM/mesh-llm). Block's engineering post: "Prompts and data sent to another machine are visible to that machine's owner, so ... Share compute with people you trust"; results from other machines "are not verified" (https://engineering.block.xyz/blog/buzz-sharing-compute-powered-by-meshllm). Invite tokens "can expire"; the CLI rotates node and owner certificates (`research/COMPETITORS.md`, mesh/docs/MESHES.md and CLI.md).
- Ahead: a split mode behind `--split`; relays through iroh for reach beyond the local network (https://www.iroh.computer/blog/mesh-llm); public meshes via Nostr discovery; macOS, Linux and Windows builds for CPU, CUDA, ROCm, Vulkan and Metal; certificate rotation documented.
- UCompute differs: your own devices only, one local network, no public mesh, no relay; per-device pinned keys instead of a shared invite token [`transport`]; an audit log of off-device requests [`audit`]. Node-removal procedure in Mesh LLM: none found on the pages read (**unverified** absence).
- Do not say: anything about split-mode speed; "Mesh" as if it were UCompute's alone: the sub-brand collides with Mesh LLM and with projects named MeshCompute and LocalMesh (`research/raw/search-demand.md` section 12), so every UCompute Mesh mention needs the whole-request sentence beside it.

### 4.5 exo (Apache-2.0, 48.1k stars)

- Their words: "Run frontier AI locally." It "figures out the best way to split your model across all available devices"; "Devices running exo automatically discover each other - no manual configuration"; "Guest Wi-Fi and some office networks may block device discovery"; "Currently, exo runs on CPU on Linux" (https://github.com/exo-explore/exo). On authentication: "this is intended behaviour, exo's api is unauthorized" (https://github.com/exo-explore/exo/issues/1833). Manual peering: "Bootstrap peers has been temporarily removed" (https://github.com/exo-explore/exo/issues/2271).
- Ahead: genuine partitioning with pipeline and tensor parallelism; RDMA over Thunderbolt 5; Claude Messages, OpenAI Responses and Ollama-compatible endpoints; a macOS app that updates itself; the largest community of any multi-device project.
- UCompute differs: it solves a different problem. Each request runs whole on one device; UCompute does not split a model [`mesh-pair-choose`]. The reason is stated as an engineering position with others' measurements, not as a speed claim: Apple's MLX team writes that pipeline parallelism "does not speed up decode" and tensor parallelism "depends on very low-latency interconnect" (https://machinelearning.apple.com/research/mlx-distributed-inference); an independent MLX tool documents a small model running slower when sharded across two Macs (https://mlx-optiq.com/docs/cluster). Where discovery is blocked, paired devices connect by address and the key is still required [`connect-by-address`]; pairing is authenticated [`transport`]. The corollary is conceded: whole-request routing cannot run a model larger than the device you choose.
- Do not say: "exo is insecure"; exo's own speedup numbers; "not pooling" as if it were a feature rather than a scope.

### 4.6 llama.cpp, llama-server and the RPC backend (MIT, 132.8k stars, b12002 on 30 Oct)

- Their words: "LLM inference in C/C++" (https://github.com/ggml-org/llama.cpp). RPC README: "This example and the RPC backend are currently in a proof-of-concept development stage. As such, the functionality is fragile and insecure. Never run the RPC server on an open network or in a sensitive environment!" (https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md). SECURITY.md: do not use the RPC backend in untrusted environments; verify weights against a known-good hash (https://github.com/ggml-org/llama.cpp/blob/master/SECURITY.md). Advisory GHSA-j8rj-fmpv-wcxw (CVE-2026-34159, CVSS 9.8, unauthenticated RCE in the RPC backend, published 26 March 2026) (https://github.com/ggml-org/llama.cpp/security/advisories/GHSA-j8rj-fmpv-wcxw). Consistency note: the ready piece `2026-10-31-loopback-rpc-vs-authenticated-transport.md` records the CVE as fixed in b8492 from the MITRE record; the advisory page as read for the OSS-infra lens listed no patched version. Both sources are cited there; keep the ready piece's wording.
- Ahead: it is the engine UCompute runs, and it is credited as such [`engine`]; every backend from CPU to Metal, CUDA, HIP, Vulkan and SYCL; `llama-server` with `--api-key`, `--fit` on by default, Responses and Anthropic Messages routes, tool use, a web UI (https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); the llama.app tray app and `llama serve` on `localhost:9931/v1` (https://llama.app).
- UCompute differs: UCompute never exposes an RPC server; a whole request crosses the network over an authenticated QUIC and TLS 1.3 channel to a paired device [`transport`, `mesh-pair-choose`]; the engine archive is verified against its published hash before it starts [`engine`]. The honest answer to "why not just `llama serve`?": for one machine, llama.cpp's own server does what UCompute Run does and more; UCompute's distinct part is the paired-device policy layer in section 2 and the pre-download verdict.
- Do not say: anything that reads as criticism of llama.cpp. Its authors describe their own feature; UCompute quotes them with the link and credits the engine in every artifact (the attribution norm this audience enforces: https://news.ycombinator.com/item?id=44003741).

## 5. Voice

Technically credible, plain, specific, limits stated first.

1. The first line of anything public is the status: development build, October 2026; UCompute is in development; no public release or download yet [`no-release`]. The five ready pieces already open this way.
2. Limits before features. Each Mesh description carries "each request runs whole on one device; UCompute does not split a model across devices" and "same local network" in the first paragraph. Each Run description carries the two demonstrated machines and "no platform is declared supported yet".
3. Every product sentence maps to a claim id and keeps its qualifier beside it; `scripts/claims_lint.py` must pass. Numbers appear only with model, hardware and build qualifier; tokens-per-second figures always say "path check, not performance".
4. Name the engine and its pinned build in every artifact. The audience polices llama.cpp attribution (https://news.ycombinator.com/item?id=44003741, https://news.ycombinator.com/item?id=48846153).
5. Quote competitors in their words with the link. Never characterise a project as lacking what its page merely does not mention. Never "insecure" about anyone else; the market's own reports and the projects' own documents say what they say.
6. Say the unverified things before anyone asks: tool calling is not yet verified; Linux is planned; pairing between two Macs is not yet shown to work; installers are not signed or notarized; no relay; no mobile. The Show HN record shows the cost of letting an audience find a gap (https://news.ycombinator.com/item?id=36802582).
7. Direction is labelled direction, every time, and never appears next to anything that sounds available [`direction`]. In the self-hosting and decentralised-training communities, credits are read as a token play (`research/raw/audience-homelab-selfhosting.md` section 5.7; `research/raw/audience-oss-infra-and-researchers.md` section 2.9). Keep it out of technical posts.
8. Plain prose, written by a person, short. Hacker News bans generated text and automated posting (https://news.ycombinator.com/newsguidelines.html); dev.to requires AI disclosure and bars AI-assisted posts that promote the author's own project (https://dev.to/guidelines-for-ai-assisted-articles-on-dev); Lobsters counts content "created without meaningful human authorship" as spam (https://lobste.rs/about). Automation schedules and distributes; it does not write the public text.
9. The project speaks as UCompute. No person is named, no invented humans, no testimonials.
