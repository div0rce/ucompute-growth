## 1. One-page summary

### What works today (verified, on named hardware only)

1. **UCompute Run: local AI inference.** A small open model in GGUF format runs on the computer itself through a pinned llama.cpp engine (release b11609). It streams output, can be cancelled, checks that a model fits in memory before loading it, verifies every download against a pinned SHA-256 hash and offers a local OpenAI-compatible API. All of this is verified on one Apple M2 MacBook Air running macOS 26.2. A Windows 11 laptop (Intel Arc 140V GPU) and a second Mac (Apple M2 Pro; that platform remains PLANNED per §27.1) have also run it. New in draft 3: one Linux desktop computer (Intel Core i9-9900K, Ubuntu 26.04, processor only) ran the fixture model to its golden output on 2026-10-23; Linux remains PLANNED as a consumer and provider platform (§27.1), and its first test run found open defects (section 4).
2. **UCompute Mesh: private remote execution between your own paired devices.** Two devices on one local network pair with a short code and can then send a whole request to run on the other device. On the home Wi-Fi network and the phone hotspot tested, they found each other (open defects: a live device once dropped off the Mac's nearby list for more than 15 s, and a just-started device's first record of the Mac had only link-local addresses; section 4.1, N1 and N2); on a network that does not pass discovery (campus Wi-Fi) they pair and reconnect by address. The connection is encrypted and both ends authenticate. Verified between a Mac and a Windows laptop through the daemons (most recently on 2026-10-22, with builds from before the fix rounds) and, new in draft 3, between that Mac and the Linux computer on a home Wi-Fi network on 2026-10-23, with the fixed builds, through the daemons (the Linux computer served the Mac on its processor). Through the apps' windows: the 2026-10-19 demonstration (section 3.2) and, on 2026-10-22, the Windows firewall consent step and pairing started in the Windows app, both done by hand. UI pairing (F-10-05) remains IMPLEMENTED_UNVERIFIED.
3. **Safe defaults.** By default no inference request leaves the device. Another device can receive work only after the user pairs it and allows it. A revoked device was cut off within a tenth of a second in four two-machine runs (three Mac–Windows, one Mac–Linux), and in tests and in the five two-machine runs that checked it (two on 2026-10-18, one on the 2026-10-19 hotspot, one on 2026-10-22, one on 2026-10-23), audit logs contained no prompt or response text.

### What does not exist (never imply it does)

| Distinction | What exists | What does **not** exist |
|---|---|---|
| Remote inference vs. pooling | Whole-request remote execution (spec Mode B). Each request runs entirely on one device the user picks. A design for splitting one model between two devices is Proposed (ADR-0005, 2026-10-23), with an implementation plan; nothing of it is built | Splitting or partitioning one model across devices, pooling memory or GPUs, running a model too big for any single device. Pooling is not implemented or verified (Gate D; F-03-* NOT_STARTED) |
| Private Mesh vs. public Swarm | A private Mesh of devices the user paired, on one local network | An open or public network, contributing to strangers, a public relay, connections across the internet (Swarm/Mode F disabled; F-02-06 NAT traversal and relay NOT_STARTED; Gate F not verified) |
| Planned credits vs. billing | A binding design principle for future compute credits (D-019, spec §26.5) | Credits, earning, purchases, prices, fees, billing, payments, payouts, trusted-access allowlists, sharing modes. U-05 and F-07-01..11 are NOT_STARTED; F-07-12 (token-incentive feasibility) is IN_PROGRESS as research only. No §26.5 stage is authorized |
| Development builds vs. releases | Development builds: macOS ad-hoc signed and not notarized, Windows without a code-signing certificate, and on Linux a daemon built from source on the test machine (no installer, no desktop app). The project installed or ran them on its 4 test machines | Any public release, download, signed or notarized installer, Linux package, auto-update or alpha/beta cohort (B-007, B-008; Gate G incomplete; §31: no cohort started) |
| Protocol aspiration vs. interoperability | One implementation's peer protocol, EXPERIMENTAL. A local HTTP API that the official OpenAI client libraries work against | A second, independent implementation of the peer protocol, a stable protocol version, independently verified interoperability (U-01 NOT_STARTED; B-018) |

### Coverage at a glance

- **Four physical machines in total:** an Apple M2 MacBook Air (macOS 26.2), an Apple M2 Pro MacBook Pro (macOS 15.7.9), an HP laptop with an Intel Core Ultra 7 258V and Arc 140V (Windows 11 Home 26200) and, new, a Linux desktop with an Intel Core i9-9900K and 14 GiB (Ubuntu 26.04 LTS x86_64, CPU engine only; `docs/environment/linux-test-host.md`, 6de3487).

Other Apple Silicon, including the M2 Pro on macOS 15.7.9, is PLANNED, as are NVIDIA/AMD GPUs, Intel Macs, phones as consumers and browsers. iOS/iPadOS as an always-on provider is UNSUPPORTED, and Windows ARM64 is EXPERIMENTAL as a provisioning target only (consumer/provider PLANNED).

## 2. Labels used in this snapshot

Sections map to the spec §26.2 labels: section 3 is **Verified reality**, section 4 **Current implementation**, section 5 **Committed engineering scope**; any price, fee or economic figure is **Strategic hypothesis**. Each section 8 claim carries its label.

| Label | Meaning |
|---|---|
| **Verified reality** | Demonstrated with committed evidence for named builds, hardware and configuration. Valid only for those |
| **Current implementation** | Code exists; acceptance is incomplete |
| **Committed engineering scope** | In the ledger or backlog; not implemented |
| **Strategic hypothesis** | An experiment or decision, including every economic figure |

Platform support uses only the spec §27.1 terms: SUPPORTED (passed a stable release gate; **none yet**), EXPERIMENTAL, PLANNED and UNSUPPORTED. A claim can be Verified reality while its platform is EXPERIMENTAL or PLANNED: the label describes the evidence, the support term describes the platform.

The "Evidence scope" column in the tables uses these terms:

- **TWO-MACHINE**: two different physical computers.
- **REAL**: one physical machine with the real engine.
- **SINGLE-HOST**: several daemon processes on one machine, or a test suite on one machine. It proves protocol and policy behaviour, and it never supports a claim about two machines (D-004).

The site uses the §26.2 labels and, on the roadmap, the ledger statuses. It adds no other status words (§26.2).

### 4.2 Behaviour changes in the fix rounds (3df9438, 780c2b9)

- **Refusals before the other device has proved its key.** Since round 3, a refusal reached before the other device has proved its key on the control stream reads `peer_unauthorized` ("did not prove it is <name>"), and the dial goes on to the next address. So a device that was revoked by its peer **no longer reads `peer_revoked` on a new dial**; it reads `peer_unauthorized`. Reason: on the network path such a refusal can be forged, so it is not trusted as the device's own verdict (ADR-0003 §9.3). Since round 5 the same holds for a claimed protocol mismatch or a frame-size close before that proof (a mismatch claim adds the hint to update both devices), so a "protocol incompatible" result is now always proven. **Seen on hardware on 2026-10-23** (177f7ed): the revoked Mac read `peer_unauthorized` while the Linux daemon recorded its own signed revocation and its refusal of the Mac as revoked. The 2026-10-18/19/22 revocation results in section 3.2 were made with earlier builds that read `peer_revoked`; the claim that the next request is refused is unchanged.
- **Disconnect hold.** A hold now survives a Sharing change and ends with Connect, unpair, revoke, a peer's revocation of the held device, networking off and on, or a service restart. The Sharing and Connect parts are shown on the Mac–Linux pair (section 3.2).
- **Protocol minor 1.** Revocations now cross a hold: each time the held device dials, the two exchange the revocations due before the close, so delivery waits for the held device's next redial (backoff at most 300 s). No message or field was added. Older builds of the same implementation still connect: the two devices negotiate the lower minor (F-08-10; SINGLE-HOST; not interoperability). A held minor-0 peer gets the old close (`CLOSE_HELD`) with no exchange; a minor-1 device held by a minor-0 build reads `peer_unauthorized`, not `peer_held`. Minor-1 builds on the test machines now: the installed ffe1a47 Mac app and the Linux daemon built for runs; both showed minor 1 on 2026-10-23, and revocations crossed a hold between them. Still minor 0: the Windows 593d4ea app and the second Mac's 6ab9f8b app. Mixed minors have not run on two machines. Known limit: two devices that hold each other exchange nothing until one connects.

## 6. Known limitations

- **Hardware and OS coverage.** Four machines: Apple M2 on macOS 26.2, Apple M2 Pro on macOS 15.7.9, Intel Arc 140V on Windows 11 Home 26200, and an Intel Core i9-9900K on Ubuntu 26.04 with the CPU engine only. There is no mobile device (B-003). There are no NVIDIA, AMD or Intel Mac results, and no GPU engine on Linux. The Mac-M2Pro evidence covers the packaged app and a partial Mesh run only; the Linux evidence covers the daemon only (no desktop app, no package) and its first test run found open defects (B-004 stays open). No platform is SUPPORTED.
- **Small models only.** The development Mac has 8 GB (B-010). Inference evidence uses stories15M, stories260K, SmolLM2 360M and Qwen2.5 0.5B; the largest model measured, for memory planning only, is Qwen2.5 1.5B q4_k_m. Memory estimates are calibrated for llama.cpp b11609 on Apple Silicon.
- **One local network.** Mesh evidence covers two devices on the same Wi-Fi network or phone hotspot. There is no relay, no NAT traversal and no path across the internet (F-02-06 NOT_STARTED).
- **Internet on first run.** The engine and models are downloaded on first use. With networking switched on (off by default), a device announces itself on the local network for discovery and pairing. Operation with no internet is untested (X-20 NOT_STARTED).
- **Networks that drop multicast, and missed announcements.** On eduroam, automatic discovery fails because the network does not pass mDNS between clients. Pairing, connect at address and remote execution still work there (2026-10-18 and 2026-10-22). Discovery was verified on a phone hotspot and on a home Wi-Fi network; on the home network the Mac's nearby list once lost a live peer for more than 15 s, and a just-started Linux daemon first saw only link-local addresses (findings N1 and N2, open).
- **Windows Firewall.** The app's consent step adds a rule for Private networks only, so the laptop's network profile must be Private (the owner set it). The consent step and pairing started on Windows work with the 593d4ea build (2026-10-22). The later changes to how the app reads its rule (75a0a89, ffe1a47) have not run on Windows.
- **macOS firewall (suspected).** One Mac-to-Mac pairing failure on 2026-10-21 may come from the macOS application firewall blocking a newly built, ad-hoc-signed app. The cause is not established.
- **Unsigned or ad-hoc builds.** macOS builds are ad-hoc signed and not notarized, so `spctl` rejects them and a downloaded copy needs "Open Anyway" once. Windows builds carry no code-signing certificate (B-008). On Linux the daemon is built from source on the test machine.
- **No public release.** There is no binary download, no WP-08 release record, no executed CI pipeline, no alpha or beta cohort and no published source (B-007, Gate G, §31).
- **Fixture numbers are path checks.** stories15M tok/s figures say nothing about real-model performance: the 15M fixture even runs faster on CPU than on Metal, and on Linux-i9's CPU it ran faster than on the Mac's Metal. The fixture's weight license is unverified, so it is never redistributed (B-011). The 0.5B and 360M numbers come from 3 runs on one machine, not a controlled study.
- **Builds behind the evidence differ by machine.** The fixed builds (rounds 1–5) have run on two machines only as the Mac-M2 app and the Linux-i9 daemon, through their APIs (177f7ed). Win-Arc still runs the pre-fix 593d4ea app, Mac-M2Pro the 6ab9f8b app. Every two-machine run since 2026-10-19 drove the apps' daemons through their APIs, except the firewall step and pairing started on Windows, which were done by hand on 2026-10-22.
- **Test hosts sleep or go offline.** The tester's Mac slept twice during the 2026-10-21 run; the laptop's battery died at 22:05 UTC on 2026-10-22, and it has been offline since (11ec77b). The development Mac slept and hibernated on 1 % battery during the round-5 final check (that binary's first-run verdicts are void; the affected test passed alone). Nothing has been tested about the product's own behaviour across sleep and wake.
- **Load-sensitive results.** Tests on Mac-M2 often run at high load from other processes. The flood-test failures there are determined environmental within stated limits (section 4); on Linux-i9's CPU engine the same tests fail on a quiet machine, undetermined.
- **Crash cleanup on Linux.** A crashed daemon's engines are not reaped on Linux under a per-user service manager (test failure, e3c2ece; open).
- **Transport privacy only.** Encryption protects traffic between paired devices. The device that runs a request necessarily processes the prompt, so there is no confidential-computing or provider-blind execution (F-06-11 research only). The packet-capture proof is SINGLE-HOST; no LAN capture was taken.
- **Windows key-file protection.** The identity files on Windows inherit the profile folder's access rights; the product sets none of its own, and a second account's access is untested (B-017).
- **Accessibility.** No screen reader has been run against an installed app on either OS; the evidence is automated checks and accessibility-tree dumps. The NVDA test is authorized (D-022), not run.
